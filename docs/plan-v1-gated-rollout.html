Russia connectivity: gated rollout plan

Every phase answers one question. Money and time go into the next phase only after the current gate passes.

Prepared 5 November 2026 for the implementing agent. Censorship in Russia changes week to week; re-check Appendix D before starting Phase 2.

How to use this plan

  • Run phases in order. Do not start a phase until the gate before it has passed, except where Parallel work says otherwise.
  • For every gate, keep the evidence listed in the Gate summary in a run log (a plain document with dates, logs and screenshots).
  • Thresholds are defaults. Change one only with a written reason in the run log.
  • Keys, passwords, subscription links and configs never go into this document, chat logs or the run log. They live in a password manager (see Appendix E).
  • The user is a confident computer user but not a network specialist. Give step-by-step instructions, ask yes/no questions, and make the technical decisions yourself.

What we are building

  • Two servers at different non-Russian providers, in different countries and networks. Each runs 3x-ui (Xray) with VLESS + Reality using its own domain for camouflage (“self-steal”) and VLESS + XHTTP, plus AmneziaWG 3.1 installed by the Amnezia app.
  • Two identical routers (GL.iNet Beryl AX preferred) on official OpenWrt with Podkop. Podkop’s URLTest switches automatically between both servers’ VLESS + Reality links. Travelmate handles hotel Wi-Fi. Two Wi-Fi networks: WORK (everything through the tunnel) and DIRECT (no tunnel).
  • Phones and the personal laptop use apps directly: a subscription client (Hiddify, Happ or v2RayTun) with both servers, and the Amnezia app with AmneziaWG 3.1 keys.
  • Commercial backup: Amnezia Premium, bought close to departure.
  • Monitoring: a scheduled probe on RU-PC until arrival.

  1. 0.1
    Employer authorization. User Confirm with the employer that working from Russia and connecting GlobalProtect and AWS Client VPN from there is permitted, and that RU-PC may be used for network tests and test software. Do not design the setup to disguise the work location from the employer. If remote work from Russia is not permitted, the work-laptop track (Phases 4–5) loses its purpose; the personal track continues.
  2. 0.2
    RU-PC audit. Agent
    • Operating system and version, admin rights, ability to install software (curl, a proxy client, Python if needed).
    • Remote desktop stability over at least two hours; whether the machine can stay on overnight.
    • Public IP, its ISP name and ASN (for example from ipinfo.io). It must be a Russian ISP, not a data center or a foreign proxy.
    • Whether outbound UDP and TCP on ports other than 443 work.
    • Whether a corporate proxy intercepts TLS: inspect the certificate issuer of a known HTTPS site.
  3. 0.3
    Service inventory. User and agent Build services.txt with one URL per line, tagged by group:
    • A: blocked in Russia, must go through the tunnel.
    • B: Russian services (banks, Gosuslugi, Yandex, marketplaces), must go direct.
    • C: foreign services that refuse Russian IPs (AI services, some banks and streaming), tunnel only, no leaks.
    • D: work endpoints: the GlobalProtect portal hostname and the AWS Client VPN endpoint hostname, protocol and port from the .ovpn file.
  4. 0.4
    Direct baseline from RU-PC, no tunnel. Agent Run test T4 (Appendix A) without the proxy flag. Record which group A sites fail (expected) and which group B sites work. For group D: DNS resolves, TCP 443 connects, and the GlobalProtect prelogin page loads (Appendix A, D-checks).
  5. 0.5
    Open the run log and store the audit notes and baseline output. Agent

Gate G0: is RU-PC a usable and representative probe?

Pass when

  • Test tools install and run.
  • The remote session stays up for two hours or more.
  • Traffic leaves through a Russian ISP, not a data center or foreign proxy.
  • At least some group A sites fail directly, which proves filtering is applied on this line.

If it fails

  • Switch to Branch F3: friends’ phones become the primary probes, with Phase 3 procedures used earlier and more often.
  • If a corporate proxy blocks all non-web traffic, results will be too pessimistic: never reject a protocol on RU-PC evidence alone.

G1

This is the main go/no-go. If no protocol passes, routers, annual plans and the domain are all wasted. Rent the shortest billing period available.

Never enable a full-tunnel VPN on RU-PC. It will cut the remote desktop session. Use local proxy mode, split tunnelling, route-nopull for OpenVPN, or limited AllowedIPs for AmneziaWG.

  1. 2.1
    Rent server A and server B at the two best providers from G1. Harden both: SSH keys only, password login off, firewall allowing only SSH, 443/tcp and the AmneziaWG UDP port, automatic security updates.
  2. 2.2
    Deploy the stack on each server.
    • 3x-ui (Xray). Inbound 1: VLESS + Reality on 443/tcp; for now use a neutral, non-brand camouflage site, never Google, Microsoft, Apple or other big brands. Inbound 2: VLESS + XHTTP.
    • Panel reachable only through an SSH tunnel, never exposed publicly.
    • AmneziaWG 3.1 installed from GE-PC with the Amnezia app. Do not install the app’s own Xray container: it would conflict with 3x-ui on port 443.
  3. 2.3
    OpenVPN probe (feeds G4). Run a temporary OpenVPN server on server B (UDP 1194 and TCP on a spare port). Connect from RU-PC with route-nopull and keep it up for ten minutes. AWS Client VPN uses OpenVPN, so if this is blocked, AWS Client VPN will be too. Remove the OpenVPN server afterwards.
  4. 2.4
    Reference check from GE-PC: each profile connects, the visible IP is the server’s, DNS leak test is clean, throughput is recorded.
  5. 2.5
    Tests from RU-PC for every server and profile: T1 port reachability, T2 three-minute series, T3 50 MB download, T4 service list through the tunnel, T5 24-hour soak (Appendix A). AmneziaWG goes through split tunnelling only.
  6. 2.6
    Domain and self-steal. Buy a non-.ru domain at an international registrar with privacy protection. Point it at server A (and a subdomain at B). Run a small web server with a valid certificate on each server and switch Reality to camouflage as that site. Re-run T1–T4.
  7. 2.7
    Fill the pass matrix: server × profile × test, with links to logs.

Gate G2: do the protocols survive from Russia?

Pass when, on both servers

  • At least one VLESS profile passes T2 with 9 of 9 requests.
  • T3 completes without a stall longer than 10 seconds.
  • T4 reaches every group A and C service.
  • T5 succeeds in 97% or more of checks over 24 hours.
  • Median throughput is at least 20 Mbit/s, or half of RU-PC’s direct speed, whichever is lower.
  • AmneziaWG 3.1 results are recorded; they matter for phones, not for routers.

If it fails

  • Iterate, up to three rounds: new IP from another /24, different camouflage site or browser fingerprint, switch to XHTTP, swap in the next provider from G1.
  • Still failing: Branch F1. Do not buy routers before G2 passes.

  3. 5.3
    Flash official OpenWrt. Choose the stable release that Podkop and the needed packages support on that day. Have the recovery procedure ready before flashing (U-Boot web recovery on GL.iNet, vendor intermediate firmware on Cudy).
  4. 5.4
    Configure.

    • MSS clamping on; WAN tested with MTU 1492 to imitate Russian PPPoE lines.
    • Strong admin password; remote and cloud management off.
  5. 5.5
    Tests in Georgia, T6–T10 (Appendix A): function, failover, a full work session with both corporate VPNs, every WAN mode, three-day burn-in.
  6. 5.6

Appendix A. Test procedures

All tunnel tests use a client that exposes a local SOCKS5 or mixed proxy at 127.0.0.1:1080. On Linux use xray-core or the sing-box CLI. On Windows use the sing-box CLI, v2rayN or Hiddify and substitute their local port. Windows 10 and later include curl.exe; run the bash examples in WSL or Git Bash, or adapt them to PowerShell.

T1. Port reachability

nc -zv -w5 SERVER_IP 443
# Windows PowerShell:
Test-NetConnection SERVER_IP -Port 443

T2. Three-minute series

Some blocks trigger only after the first kilobytes or after a delay, so a single request proves nothing. Pass: 9 of 9 responses with a 2xx or 3xx code.

for i in $(seq 1 9); do
  curl -s -o /dev/null -m 20 --socks5-hostname 127.0.0.1:1080 \
    -w "$(date +%T) %{http_code} %{time_total}s\n" https://www.instagram.com
  sleep 20
done

T3. Large download

Catches freezes after about 16 KB and measures throughput. Pass: completes, no stall over 10 seconds.

curl --socks5-hostname 127.0.0.1:1080 -o /dev/null -m 120 \
  -w "%{size_download} bytes, %{speed_download} B/s\n" \
  "https://speed.cloudflare.com/__down?bytes=50000000"

T4. Service list

Run once through the tunnel and once without --socks5-hostname for the direct baseline.

while read url; do
  printf "%-45s " "$url"
  curl -s -o /dev/null -m 15 --socks5-hostname 127.0.0.1:1080 -w "%{http_code}\n" "$url"
done < services.txt

T5. Soak

Run one client instance per server and profile on its own local port (1081, 1082 and so on). Schedule the probe every 5 minutes with cron or Windows Task Scheduler. Pass: 97% or more rows return 204 in under 5 seconds over 24 hours.

# probe.sh LABEL PORT
ts=$(date -u +%FT%TZ)
r=$(curl -s -o /dev/null -m 20 --socks5-hostname 127.0.0.1:$2 \
     -w "%{http_code},%{time_total}" https://www.gstatic.com/generate_204)
echo "$ts,$1,$r" >> soak.csv

D-checks. Corporate endpoints

TLS reachability only; no credentials are used. Run direct and through the tunnel.

curl -sv -m 15 -o /dev/null https://GP_PORTAL/global-protect/prelogin.esp

For AWS Client VPN, rely on the OpenVPN probe from step 2.3; a reachable port does not show whether the OpenVPN handshake itself is blocked.

Appendix D. Known constraints, November 2026

  • Plain WireGuard and OpenVPN are blocked in Russia since February 2026.
  • Filtering judges traffic behaviour after roughly the first 16 KB, checks whether the camouflage site matches the hosting, and since August 2026 blocks whole subnets of hosters popular with VPNs. Rollout differs by ISP and region.
  • Large clouds (AWS, DigitalOcean, OVH, Oracle Cloud, Scaleway, Akamai, Hetzner) are often throttled from Russia.
  • Data-center networks inside Russia are filtered less than home ISPs, which is why RU-PC on an office ISP is a better probe than a Russian VPS.
  • Mobile internet in many regions periodically switches to whitelist mode; only allowlisted IPs are reachable and no tunnel helps.
  • AmneziaWG 1.5 and 2.0 have become vulnerable to blocking; Amnezia recommends 3.1 for self-hosted servers. Versions 2.0 and 3.1 share one container and cannot run side by side from the app.
  • Router firmware (Keenetic, OpenWrt, GL.iNet) does not support AmneziaWG 3.x yet, so routers use VLESS.
  • Podkop is in beta, needs OpenWrt 24.10 or later, and its URLTest mode does not accept XHTTP links.
  • Since 2026, Russian hosting providers may not host VPN infrastructure. FirstVDS suffered a breach on 17 October 2026 that exposed root passwords and SSH keys.
  • Many popular Russian apps detect an active VPN, so split tunnelling for Russian services is required.

Appendix E. Security rules

  • Secrets live only in the password manager, with an encrypted offline copy. Never in this document, the run log, chats or email.
  • Servers: SSH keys only, password login off, firewall with the minimum open ports, automatic security updates, panels reachable only through an SSH tunnel.
  • Every person and device gets its own client key, so one can be revoked without touching the others. Friends’ keys expire.
  • Routers: strong admin password, remote and cloud management off, configuration backed up after every change.
  • A lost or stolen router means revoking its keys on both servers the same day.
  • RU-PC: install only what the tests need and remove test tools after Phase 7 unless monitoring still runs; follow the employer’s rules for that machine.
