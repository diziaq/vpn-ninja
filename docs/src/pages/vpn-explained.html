How the VPN chain works, and why we check so much

Your traffic has to cross a Russian filter that judges four things: where it goes, what protocol it looks like, which site name it mentions, and how it behaves over time. Each check in the plan tests one point in the chain where the filter can cut it. The server side is built and verified, and on 8 November the tunnel passed its first test from Russia: 4 of 5 variants, all three Vision fingerprints, 6 of 6 repeated requests, a complete 20 MB download at up to 20.5 Mbit/s on a ~28 Mbit/s office line. Still untested: home ISPs, long runs and the work VPNs.

1. The chain: every hop your traffic makes

A web page or a work VPN connection from Russia passes six points. A failure at any one of them breaks everything after it, which is why the plan tests each point separately instead of only asking "does the VPN work?".

2. How the Russian filter decides what to cut

Every Russian ISP must install a TSPU box from the regulator (Roskomnadzor) in its network. It reads the traffic as it passes (deep packet inspection, DPI) and can drop, slow or reset connections. It does not need to break the encryption: the outside of a connection already tells it a lot. It applies roughly five tests. Each card says what it looks at and how our setup answers it.

TEST 1

Where is it going?

Lists of blocked addresses. Since August 2026 whole address blocks (subnets) of hosters popular for VPNs are blocked. From the Russian PC, Hetzner, OVH and Linode were completely blocked.

Answer: hosters that tested clean from Russia (Time4VPS, BuyVM) and a second server at a different hoster as a spare.

TEST 2

What protocol is it?

Classic VPNs have recognisable handshakes. Plain WireGuard and OpenVPN have been blocked since February 2026 by exactly this test.

Answer: VLESS over TLS 1.3, byte for byte the same shape as a browser opening an HTTPS site.

TEST 3

Which site does it name?

The first message of an HTTPS connection carries the site name in plain text (the SNI field). Names of blocked sites are cut immediately.

Answer: the tunnel names an ordinary, unblocked site (the camouflage site), not the real destination.

TEST 4

How does it behave?

The filter lets a suspicious connection start, watches it, and silently stalls it after about 16 KB. From the Russian PC a Vultr Frankfurt download froze at exactly 15,957 bytes.

Answer: Vision flow-control hides the typical "tunnel inside TLS" rhythm; we test big downloads and long runs, not just one page.

TEST 5

What is the server really?

A censor can connect to a suspicious address itself and see whether a real website answers (active probing). This is documented for China's filter; general knowledge, not confirmed for Russia.

Answer: Reality: anyone without our key is passed through to a real website and sees its real certificate.

BEYOND REACH

Whitelist mode

In many regions mobile internet is sometimes switched to "only allowlisted addresses". Then no tunnel to a foreign server can work.

Answer: none technical: use home or hotel Wi-Fi via the router; friends' tests record when it happens.

3. How VLESS + Reality hides the tunnel

Xray is the program on the server and on your devices. VLESS is its lightweight tunnel protocol. Reality is the disguise: it makes the server look, to everyone except you, like an ordinary website that belongs to someone else.

The three extra knobs we test

  • Browser fingerprint (chrome, firefox, safari). Every browser builds its opening TLS message slightly differently. Xray copies one of them exactly (uTLS). Filters have been known to target one specific fingerprint, so we test three and keep the one that survives.
  • Vision (port 443) vs XHTTP (port 8443). Vision hides the give-away pattern of "an encrypted connection inside an encrypted connection" by passing the inner encryption straight through. XHTTP instead chops traffic into ordinary-looking HTTP requests. They fail in different ways, so having both doubles the chance one passes. The router's failover (URLTest) accepts only Vision, which is why Vision matters most.
  • Camouflage site. The name in the opening message. Today it is a neighbour's site; the next section explains why we want our own.

4. Why we want our own domain for the camouflage

Reality has to name some real site. Today our server names a neighbour's site: a small website on another server in the same hoster network. That works: Phase 2b passed with it from the Russian PC on 8 November. Our own domain ("self-steal") fixes three weaknesses of borrowing a stranger's site.

1. Consistency

A filter can look up the site name in public DNS and compare it with the address actually contacted. With a neighbour's site they disagree. With our domain they agree. We do not know that the Russian filter runs this check today; it is cheap for it to add.

2. Independence

Reality copies the camouflage site's live TLS behaviour. If the neighbour switches off TLS 1.3, changes certificate, moves, or goes offline, our connections start failing or start looking wrong. Our own site changes only when we change it.

3. Plausible traffic

A tunnel moves gigabytes. Gigabytes a day to a stranger's hobby site stand out; to "your own site on your own server" they look like a personal cloud or backup.

Cost and trade-offs. About $10 a year at an international registrar, a non-.ru name, with WHOIS privacy. The name itself can be blocked; then we buy another, which is cheap and fast. It also adds a small web server with an auto-renewing certificate to maintain.

Why not now. The neighbour's site passed Phase 2b from Russia, so the own domain is an upgrade for longevity, not urgent. We add it later and re-run the same test; if the tunnel ever starts failing, it is one of the first fixes to try.

5. Why the work laptop probably needs the router

Your work laptop runs two corporate VPNs. Neither is built to hide from a censor:

  • AWS Client VPN is built on OpenVPN, and plain OpenVPN has been blocked in Russia since February 2026. Directly from a Russian network it will very likely be cut by test 2.
  • GlobalProtect normally uses IPsec over UDP port 4501, with an HTTPS fallback. Its portal answered from the Russian PC, but its actual tunnel is untested.

Wrapped inside our outer tunnel, the filter never sees either of them: it sees only the outer VLESS + Reality connection. Doing that wrapping on the laptop would mean installing our VPN software on a company-managed machine. The router does it outside the laptop: the laptop just joins the WORK Wi-Fi network and runs its corporate VPNs as usual. That is gate G4, and the planned OpenVPN probe decides it.

One technical cost: a tunnel inside a tunnel leaves less room per packet (MTU). The router script clamps packet sizes (MSS clamping) so the inner VPN does not stall on large transfers.

6. Why we check so many details

Censorship failures are often partial: the first page loads, then a big file freezes; it works at noon and dies in the evening; it works on the office line and not at home. A single "it connected" proves very little. Each detail below catches one specific failure that a simpler test would miss.

8. What unblocks what

The plan is gated: the cheapest question that can kill the plan goes first, and money and time go into the next step only after the current one passes. Phase 2b on the Russian PC was the bottleneck; it passed on 8 November. The monitor (at least 3 hours including the evening, decision D-18) runs next; server B follows it (decision D-17).

Can be prepared now, without the Russian PC

  • The Russian-PC package phase2b2c (built and delivered; tunnel test run and passed; monitor running next). The router twin test is still to build.
  • The own-domain setup script, ready for when the domain is bought.
  • Client management for friends' keys and the friends' instructions (G3).
  • The temporary OpenVPN probe (G4) and the router kit (G5).

Glossary

TSPU
The filtering box Russian ISPs must install; it inspects passing traffic (DPI) and drops, slows or resets connections.
DPI
Deep packet inspection: judging traffic by its contents and patterns, not just its address.
TLS 1.3
The encryption under every HTTPS site. Its first message (the "hello") is partly readable.
SNI
The site name written in plain text inside the TLS hello. Filters read it.
Xray
The program on the server and on clients that runs the tunnel.
VLESS
Xray's tunnel protocol: a thin layer that carries your traffic inside TLS.
Reality
Xray's disguise: the server borrows a real site's TLS identity; only key holders get the tunnel, everyone else is passed to the real site.
Vision / XHTTP
Two ways of shaping tunnel traffic. Vision runs on port 443 and is what the router uses; XHTTP on 8443 is the backup variant.
Fingerprint (uTLS)
The exact byte pattern of a browser's TLS hello. Xray imitates Chrome, Firefox or Safari.
Self-steal
Reality pointing at our own domain and our own small website instead of a stranger's site.
Active probing
A censor connecting to a suspicious server to see what answers.
sing-box
Another tunnel program; Podkop on the router uses it. The "twin test" runs it on the Russian PC with the router's settings.
Podkop / OpenWrt
OpenWrt is open router firmware; Podkop is an add-on that sends chosen traffic through VLESS and fails over between servers (URLTest).
SOCKS proxy mode
How we test on the Russian PC: the tunnel serves only programs that ask for it, so Remote Desktop keeps working.
MTU / MSS clamping
Maximum packet size. Tunnels in tunnels shrink it; clamping prevents stalls.
AmneziaWG 3.1
A disguised WireGuard variant for phones; older versions (1.5, 2.0) are now detectable.
